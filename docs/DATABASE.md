# Tokenly Local Data Model

## Current persistence model

The local prototype persists application records in one versioned IndexedDB database. `localStorage` is limited to small session and development preferences; it is not used for wallet, order, evidence, or audit records.

All persistence is accessed through repository interfaces. Business services must not depend on IndexedDB APIs or store names. The future Supabase model is described in `supabase/planned-schema.sql`, but that file is planning material and not a migration.

## Identifier and field conventions

- Domain identifiers are opaque strings generated by the application.
- TypeScript uses `camelCase`; future database fields use `snake_case`.
- Token amounts are positive fixed-decimal values with at most two decimal
  places.
- Money used for manual PayNow recording is stored as integer cents, never binary floating-point.
- Timestamps are ISO 8601 UTC strings in the prototype and timezone-aware timestamps in the future database.
- Metadata is a JSON-compatible object with an explicit type at the service boundary.
- Human-readable references are unique enough for event operations but are not primary keys.
- A transaction-group ID connects every record created by one business operation.
- Ledger idempotency keys are unique across the event and are never reused for
  a different operation. Other mutation records use their documented
  event-level uniqueness scope.

## IndexedDB stores

Names are logical and may be prefixed by the implementation’s data namespace.

### `accounts`

| Field                    | Notes                                                                 |
| ------------------------ | --------------------------------------------------------------------- |
| `id`                     | Opaque primary key                                                    |
| `mobileNumber`           | Legacy/local contact identifier; indexed and unique in seed data      |
| `username`               | Optional local operational login name for admin/vendor-style accounts |
| `displayName`            | Fictional name                                                        |
| `role`                   | `customer`, `vendor`, `staff`, or `administrator`                     |
| `status`                 | `active` or `disabled`                                                |
| `createdAt`, `updatedAt` | Lifecycle timestamps                                                  |

Normal account repository reads return only this credential-free shape.

### `accountPinCredentials`

| Field               | Notes                                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `accountId`         | Primary key and relationship to the account                                                                                     |
| `pinCredential`     | Nullable prototype credential representation; `null` means setup has not occurred and access remains credential-repository-only |
| `failedPinAttempts` | Local lockout simulation state                                                                                                  |
| `lockedUntil`       | Optional local lockout timestamp                                                                                                |

The credential-specific repository contract is intended only for
`PinVerificationService`; ordinary account lookup and list operations cannot
return these records. Account creation writes the account and its initial
credential atomically. Production identity, PIN hashing, and rate-limit state
will not reuse this prototype credential format.

An unconfigured credential record has `pinCredential: null`, zero failed
attempts, and no lock timestamp. First-time PIN setup replaces that null value;
subsequent changes require verification of the configured PIN.

### `customers`

| Field                    | Notes                                   |
| ------------------------ | --------------------------------------- |
| `id`                     | Customer primary key                    |
| `accountId`              | Unique account relationship             |
| `walletId`               | Unique customer wallet relationship     |
| `privateAccessCode`      | Opaque private account-link code        |
| `claimCode`              | Opaque one-time account-claim code      |
| `claimExpiresAt`         | Claim expiry timestamp                  |
| `claimedAt`              | Claim redemption timestamp, if redeemed |
| `publicCode`             | Opaque vendor-facing wallet QR code     |
| `walletQrUpdatedAt`      | Last wallet QR regeneration timestamp   |
| `onboardingCompletedAt`  | Optional completion timestamp           |
| `createdAt`, `updatedAt` | Lifecycle timestamps                    |

`claimCode` and `privateAccessCode` are not indexed in the current local
prototype; claim/private account routes scan the local customer records. The
vendor-facing `publicCode` remains indexed and is the only customer credential
inside wallet QR payloads.

### `wallets`

| Field            | Notes                        |
| ---------------- | ---------------------------- |
| `id`             | Wallet primary key           |
| `ownerAccountId` | Indexed account relationship |
| `ownerType`      | Customer or vendor           |
| `status`         | `active` or `frozen`         |
| `createdAt`      | Creation timestamp           |

There is no persisted balance field and no repository `setBalance` operation.

### `ledgerEntries`

| Field                   | Notes                                                               |
| ----------------------- | ------------------------------------------------------------------- |
| `id`                    | Unique entry ID                                                     |
| `walletId`              | Indexed wallet relationship                                         |
| `transactionGroupId`    | Indexed group relationship                                          |
| `entryType`             | Issuance, purchase, receipt, refund, settlement, or adjustment type |
| `direction`             | `credit` or `debit`                                                 |
| `tokenAmount`           | Positive fixed decimal, at most two places                          |
| `actorAccountId`        | Required actor                                                      |
| `relatedCustomerId`     | Optional indexed relationship                                       |
| `relatedVendorId`       | Optional indexed relationship                                       |
| `relatedOrderId`        | Optional indexed relationship                                       |
| `relatedEvidenceId`     | Optional indexed relationship                                       |
| `reference`             | Human-readable technical reference                                  |
| `description`           | Precise operational description/reason                              |
| `occurredAt`            | Immutable timestamp                                                 |
| `idempotencyKey`        | Indexed and unique for mutation scope                               |
| `metadata`              | Safe JSON-compatible details                                        |
| `reversesLedgerEntryId` | Optional relationship to the original entry                         |

Ledger records are append-only: repositories provide create and query operations, not update/delete.

Ledger entry semantics are type-specific:

- issuance is a customer credit linked to evidence and is not a reversal;
- purchase is a customer debit and paired vendor credit linked to the same
  customer, vendor, and order;
- refund is a customer credit and paired vendor debit, each linked to its
  original purchase entry;
- administrative adjustments may credit or debit but never reverse another
  entry;
- `vendor_settlement` is reserved as a vendor debit with only a vendor
  relationship. Current manual settlement records do not create this ledger
  entry or move wallet value.

Mutation idempotency uses prefix-free ledger keys. One primary or single entry
stores `operation:<base-length>:<base-key>` as the event-wide operation
reservation. Additional entries in a paired group store
`entry:<scope>:<base-length>:<base-key>`. The command/business record keeps the
validated base key. This prevents a base key containing an older suffix from
colliding with a genuinely scoped entry.

### `tokenIssuances`

| Field                        | Notes                                                          |
| ---------------------------- | -------------------------------------------------------------- |
| `id`                         | Issuance primary key                                           |
| `customerId`, `walletId`     | Recipient relationships                                        |
| `staffAccountId`             | Actor relationship                                             |
| `evidenceId`                 | Local evidence relationship                                    |
| `paynowAmountCents`          | Positive integer manually entered amount                       |
| `tokensPerDollar`            | Positive integer/rational rate snapshot as defined by settings |
| `tokenAmount`                | Positive fixed-decimal result, at most two places              |
| `paymentReference`           | Optional trimmed staff-entered display value                   |
| `normalizedPaymentReference` | Optional case/whitespace-normalized duplicate lookup value     |
| `note`                       | Optional operational note                                      |
| `transactionGroupId`         | Linked operation                                               |
| `reference`                  | Generated issuance reference                                   |
| `createdAt`                  | Confirmation timestamp                                         |

The rate snapshot is preserved even after event settings change. Issuance uses
fixed-decimal arithmetic rounded to at most two decimal places:
`round(paynowAmountCents * tokensPerDollar / 100, 2)`.

### `evidence`

| Field                               | Notes                                                          |
| ----------------------------------- | -------------------------------------------------------------- |
| `id`                                | Evidence primary key                                           |
| `kind`                              | Prototype PayNow screenshot                                    |
| `fileName`, `mimeType`, `sizeBytes` | Validated metadata                                             |
| `localBlobKey` or `blob`            | Local-only image storage according to the adapter design       |
| `capturedByAccountId`               | Staff actor                                                    |
| `createdAt`                         | Attachment timestamp                                           |
| `metadata`                          | Safe capture/source details; never payment-verification status |

No metadata field should imply automated PayNow verification.

### `vendors`

| Field                          | Notes                                               |
| ------------------------------ | --------------------------------------------------- |
| `id`                           | Vendor primary key                                  |
| `accountId`, `walletId`        | Unique account/wallet relationships                 |
| `publicCode`                   | Opaque vendor QR code; indexed and unique           |
| `displayName`                  | Public identity                                     |
| `logo`, `banner`               | Local asset reference or safe generated placeholder |
| `description`, `stallLocation` | Storefront content                                  |
| `operatingStatus`              | `open`, `closed`, or `paused`                       |

### `products`

| Field                                    | Notes                       |
| ---------------------------------------- | --------------------------- |
| `id`, `vendorId`                         | Product and indexed owner   |
| `name`, `description`, `image`           | Storefront content          |
| `tokenPrice`                             | Positive integer            |
| `category`                               | Vendor catalogue grouping   |
| `isAvailable`, `isSoldOut`, `isArchived` | Explicit independent states |
| `displayOrder`                           | Non-negative integer        |
| `createdAt`, `updatedAt`                 | Lifecycle timestamps        |

Historical orders retain line-item snapshots, so later product edits do not rewrite a completed order.

### `orders`

| Field                                | Notes                                                                              |
| ------------------------------------ | ---------------------------------------------------------------------------------- |
| `id`, `reference`                    | Primary and human reference                                                        |
| `customerId`, `vendorId`             | Indexed parties                                                                    |
| `customerWalletId`, `vendorWalletId` | Wallet relationships                                                               |
| `status`                             | Prototype supports immutable `completed` orders                                    |
| `items`                              | Non-empty line snapshots: product ID, name, unit token price, quantity, line total |
| `tokenTotal`                         | Authoritatively recalculated positive integer                                      |
| `transactionGroupId`                 | Purchase group                                                                     |
| `idempotencyKey`                     | Duplicate-submission protection                                                    |
| `completedAt`                        | Immutable completion timestamp                                                     |

Completed orders are never edited. Refund state is derived from refund records.

### `refunds`

| Field                               | Notes                           |
| ----------------------------------- | ------------------------------- |
| `id`, `reference`                   | Primary and human reference     |
| `orderId`, `customerId`, `vendorId` | Indexed relationships           |
| `tokenAmount`                       | Positive integer                |
| `reason`                            | Required precise reason         |
| `actorAccountId`                    | Vendor actor in the prototype   |
| `transactionGroupId`                | Refund group                    |
| `idempotencyKey`                    | Duplicate-submission protection |
| `createdAt`                         | Confirmation timestamp          |

Remaining refundable amount is calculated from the original order total minus prior refund records.

### `settlements`

| Field                                                          | Notes                                                       |
| -------------------------------------------------------------- | ----------------------------------------------------------- |
| `id`, `reference`                                              | Primary and human reference                                 |
| `vendorId`                                                     | Indexed vendor                                              |
| `periodStart`, `periodEnd`                                     | Half-open accounting period: start inclusive, end exclusive |
| `earnedTokenAmount`                                            | Calculation snapshot                                        |
| `status`                                                       | `draft`, `approved`, or `paid`                              |
| `payoutReference`, `notes`                                     | Manual operational fields                                   |
| `createdByAccountId`, `approvedByAccountId`, `paidByAccountId` | Optional lifecycle actors                                   |
| `createdAt`, `updatedAt`                                       | Lifecycle timestamps                                        |

This is a manual record only and does not initiate a bank transfer.
`earnedTokenAmount` is calculated from authoritative ledger entries whose
`occurredAt` falls within `[periodStart, periodEnd)`: vendor receipt credits
minus vendor refund debits. This half-open boundary lets adjacent periods share
an endpoint without double-counting activity at that instant.

### `auditLogs`

| Field                    | Notes                        |
| ------------------------ | ---------------------------- |
| `id`                     | Primary key                  |
| `eventType`              | Controlled audit event name  |
| `actorAccountId`         | Indexed actor                |
| `targetType`, `targetId` | Indexed target relationship  |
| `description`            | Precise operational text     |
| `occurredAt`             | Immutable timestamp          |
| `metadata`               | Safe JSON-compatible context |
| `transactionGroupId`     | Optional indexed group       |

Audit records are append-only. PINs, credentials, evidence bytes, and secrets are forbidden in metadata.

### `eventSettings`

| Field                                                   | Notes                               |
| ------------------------------------------------------- | ----------------------------------- |
| `id`                                                    | Singleton/event setting key         |
| `eventName`, `eventSubtitle`, `eventDates`, `venue`     | Public event identity               |
| `tokensPerDollar`                                       | Positive configured conversion rate |
| `supportLabel`, `supportContact`, `supportInstructions` | Customer help                       |
| `updatedByAccountId`, `updatedAt`                       | Last change trace                   |

Every setting change appends an audit record and token issuance snapshots the rate used.

### Data metadata

The database also stores a small schema/seed metadata record:

- `schemaVersion`;
- `seedVersion`;
- `seededAt`.

Version upgrades must be additive or explicitly migrate records in `onupgradeneeded`. Never clear user data during an ordinary version upgrade. Reset/reseed is a separate, confirmed development action.

Local data version `2` introduces strict ledger semantics and prefix-free
idempotency reservations. Version `3` adds one-time claim QR, private account
link, and regeneratable wallet QR fields. Version `4` changes local
operational entry to username/password for the seeded super-admin. Version `5`
replaces readable seeded private-account links with long numeric opaque links.
Older local data is rejected without mutation and requires an explicit
development reset/reseed; it is never cleared automatically.

## Required indexes and uniqueness

At minimum, adapters need efficient queries for:

- account by normalized mobile number;
- customer/vendor by opaque public code;
- wallet by owner account;
- ledger by wallet, transaction group, order, and timestamp;
- mutation by idempotency key;
- issuance by customer, staff, reference, and timestamp;
- evidence by actor and timestamp;
- product by vendor/display order and vendor/status;
- order by customer/vendor/timestamp and transaction group;
- refund by order and timestamp;
- settlement by vendor/period/status;
- audit by actor, target, event type, transaction group, and timestamp.

Compound keys or normalized unique-key stores may be used where IndexedDB cannot express a conditional database constraint. Repository contract tests must prove duplicate prevention.

## Invariants

- Ledger and audit entries are never updated or deleted.
- Every ledger mutation has an actor, transaction group, timestamp, and idempotency key.
- Token amounts use fixed precision within documented limits; quantities and
  currency minor units are safe integers.
- Wallet balance cannot become negative.
- A purchase has at least one item and uses current product data.
- One purchase group contains equal customer debit and vendor credit totals.
- One refund group contains equal customer credit and vendor debit totals.
- Cumulative refunds do not exceed the completed order total.
- Reversal entries point to original entries and preserve originals.
- Issuance tokens equal the validated conversion result and preserve the rate snapshot.
- An administrative adjustment has an administrator actor and required reason.
- A settlement’s period and eligible token total are calculated from authoritative data.

## Reset and reseed

Development reset may delete only the known Tokenly IndexedDB database after confirming its exact configured name. Reseed then writes deterministic fictional records and current metadata. This action is environment-gated, clearly labelled, and not available in ordinary production mode.

## Future adapter replacement

The following local adapters will later be replaced:

- IndexedDB account/customer repositories → Supabase Auth profile and database repositories
- IndexedDB wallet/ledger repositories → server-enforced Postgres repositories/functions
- IndexedDB issuance/evidence repositories → Postgres plus Supabase Storage
- IndexedDB vendor/product/order/refund/settlement/audit/settings repositories → Postgres repositories
- local transaction coordinator → server-side transaction/function boundary
- local session store → authenticated server session

See `supabase/README.md` for the migration boundary.
